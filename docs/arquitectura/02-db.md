# 02 · `packages/db` — modelo de datos, migraciones y lógica de base

> Parte **4** (datos y geoespacial). Última migración: **0019**. Leyenda: **[C]** confirmado en código ·
> **[I]** inferido · **[Doc]** según documentación.

## 1. Para qué existe

Es dueño del **esquema** de PostgreSQL/PostGIS y de toda la lógica que depende de él, aunque la
ejecute otro servicio [C]:

- **Migraciones SQL** versionadas y su runner con locks.
- **Cliente** (`pg.Pool`) con timeouts y una abstracción `Ejecutor` que corre igual sobre `pg` y sobre PGlite.
- **Contraseñas**: Argon2id en workers.
- **Freno de login** y de altas por IP.
- **Cuentas de staff** por CLI.
- **Puntos críticos**: DBSCAN completo e incremental.
- **Relleno de `geom_publico`**.
- **Mantenimiento**: retención.
- **Verificación de privilegios** al arrancar.
- **Seeds sintéticos** y **PostGIS local sin Docker** (PGlite).

api-core y geo-service lo importan como biblioteca. Las rutas HTTP **no** viven aquí.

## 3. Modelo de datos

```text
                          ┌──────────────┐
             ┌───────────►│   usuario    │◄─────────────┬────────────────────┐
             │ CASCADE     └──────────────┘ SET NULL     │ SET NULL            │ CASCADE
        ┌────┴────┐        ▲ autor_id / validado_por     │ subido_por          │
        │ sesion  │        │                             │                ┌────┴───────────────┐
        └─────────┘ ┌──────┴────────────────┐   CASCADE  ┌┴────────────┐  │cuota_reporte_diaria│
                    │  reporte_inundacion   │◄──────────│ reporte_foto │  └────────────────────┘
                    │  (geom, geom_publico, │            └─────────────┘
 fusionado_en_id ──►│   publicar_en, estado,│── punto_critico_id ──► ┌───────────────┐
  (self, SET NULL)  │   severidad_*, …)     │      (SET NULL)        │ punto_critico │
                    └──────────┬────────────┘                         └───────────────┘
                               │ distrito_id / unidad_vecinal_id + version_capa (relación LÓGICA, sin FK)
                               ▼
        geo.distrito_municipal · geo.unidad_vecinal · geo.manzana   (PK (id, version_capa), GIST)
                               ▲
                     geo.capa_version (una vigente por capa) → vistas geo.*_vigente

 Sueltas: auditoria (sin FK), intento_login, idempotencia (→ reporte, CASCADE), _migraciones
```

Detalle de columnas en [PROJECT_STRUCTURE_AND_FUNCTIONALITY.md](../../PROJECT_STRUCTURE_AND_FUNCTIONALITY.md) §9.

### Restricciones que la base garantiza [C]

- `descripcion` de 10 a 1000 caracteres.
- `severidad_manual` exige `severidad_motivo`.
- `publicar_en` entre `creado_en` y `creado_en + 1 h`, sin DEFAULT desde la 0016: un INSERT que la
  olvide **falla**.
- `distancia_dispositivo_m` entre 0 y 1000.
- `cuota_*_n >= 0`.
- Motivo obligatorio en `rechazado` y `duplicado`, y `fusionado_en_id` solo en `duplicado`
  (0018, validados solo si no hay filas que los violen).
- Una sola versión vigente por capa (índice único parcial).
- `lower(email)` único.

**Reglas del runner** [C]:

- Cada migración va en su transacción.
- Advisory lock `4022`, incluida la creación de `_migraciones`. Así 8 procesos simultáneos no se pisan.
- `lock_timeout` de 10 s: si vence, la migración se deshace entera (SQLSTATE 55P03) y se reintenta.
- `--hasta NNNN` existe para restaurar respaldos viejos.
- **No hay checksum** de las migraciones ya aplicadas.

## 5. Roles y privilegios [C]

| Rol | Uso | Privilegios |
|---|---|---|
| `curichi` | Migraciones, seeds, ETL, CLI de cuentas | Dueño del esquema (DDL). En Docker, además superusuario (es `POSTGRES_USER`) |
| `curichi_api` | api-core | `reporte_inundacion` S/I/U · `reporte_foto` S/I/U/D · `auditoria` **solo INSERT** · `usuario` SELECT + INSERT(email, nombre, password_hash) + UPDATE(password_hash) · `sesion`, `idempotencia`, `cuota_reporte_diaria` S/I/U/D · `intento_login` S/I/D · `punto_critico` S/I/D · `geo.*` SELECT · `capa_version` S/U |
| `curichi_geo` | geo-service | SELECT en las capas, `capa_version`, `reporte_inundacion` y `punto_critico`. Nada más |

- Los roles los crea `infra/sql/01-roles.sh` al iniciar el volumen.
- Los GRANT los dan las migraciones 0008, 0009, 0014 y 0016, **uno por uno**, sin
  `GRANT ON ALL TABLES` ni `ALTER DEFAULT PRIVILEGES`. Así una tabla nueva empieza sin permisos.

## 6. Algoritmos importantes

### 6.1 Puntos críticos (§9.2)

```text
completo:     SELECT … ST_ClusterDBSCAN(ST_Transform(geom, 32720), eps := 25, minpoints := 1) OVER ()
              FROM reporte_inundacion WHERE estado IN ('validado','resuelto')
              → por grupo: centroide exacto, centroide PÚBLICO (media de geom_publico), n, fechas,
                severidad máx., distrito/UV por PIP del centroide, diámetro (aviso > 100 m)
incremental:  semillas = reporte + compañeros de su punto anterior
              → BFS de vecinos a ≤ 25 m (prefiltro && en 4326 + ST_DWithin en el CRS métrico)
              → componentes conexas (union-find) → disuelve los puntos viejos y crea los nuevos
```

- Con `minpoints = 1`, DBSCAN es exactamente «componentes conexas a ≤ 25 m». Por eso el incremental
  es equivalente al completo [C, comentario en el código y `test/puntos-criticos-metrica.test.ts`].
- Ambos caminos toman el lock `4021`.
- Límite conocido [Doc]: con un millón de reportes densos, todo encadenó en **un solo** punto crítico.

### 6.2 Contraseñas

- `hashPassword` y `verificarPassword` envían el trabajo a workers (`node:crypto argon2Sync`).
- Si no hay workers, usan `hash-wasm` en el mismo hilo. Los dos generan el mismo formato PHC.
- Si la cola está llena, la verificación devuelve `false`: nunca hay un login «correcto por error».

### 6.3 Mantenimiento

`ejecutarMantenimiento` es idempotente y usa índices parciales. Lo programa api-core cada 6 h.

## 7. Cómo se usa

```bash
pnpm db:migrate                   # DATABASE_URL del entorno (rol dueño); sin ella → PGlite 5433
pnpm db:generate <nombre>         # crea migraciones/NNNN_<nombre>.sql
pnpm db:seed:samples              # cuentas de desarrollo + reportes sintéticos
pnpm db:local                     # PostGIS sin Docker (PGlite) en 127.0.0.1:5433
pnpm privilegios                  # matriz de privilegios contra una base REAL
pnpm --filter db puntos-criticos:recalcular
pnpm --filter db cuentas -- crear --email x@y --nombre "…" --rol tecnico   # contraseña por stdin o CUENTA_PASSWORD
pnpm --filter db test             # PGlite efímero
```

En producción el job `migraciones` del Compose corre `node node_modules/db/dist/cli/migrar.js`
con el rol dueño, **antes** de los servicios.

## 8. Cómo agregar una migración (checklist)

1. `pnpm db:generate <nombre>` y escribir SQL **idempotente**: `IF NOT EXISTS`, comprobar el
   catálogo antes de cada `ALTER` y recordar que el runner la envuelve en una transacción.
2. Si crea una tabla: decidir sus GRANT para `curichi_api` y `curichi_geo` en la misma migración y
   actualizar `src/cli/matriz-privilegios.mjs`.
3. Actualizar el espejo `src/esquema/index.ts`.
4. Escribir `test/migracion-NNNN-<nombre>.test.ts` (patrón de 0010–0019).
5. Si cambia un enum o un campo de intercambio: cambio de contrato en `packages/contracts`.
6. Pensar en «ampliar → contraer» si hay api-core viejos atendiendo durante el despliegue.

## 9. Pruebas (25 archivos) [C]

- Runner (`migrar`, `cli-migrar`) y **una prueba por migración** desde la 0010.
- Espejo Drizzle frente a la base.
- Contraseñas, cuentas y CLI de cuentas.
- Privilegios (matriz completa sin tablas olvidadas).
- Puntos críticos (métrica, volumen, entorno), configuración y servidor local.
- Todas corren sobre **PGlite** (una conexión). La concurrencia real se prueba en api-core contra
  PostgreSQL real y en el job `postgres-real` del CI.
