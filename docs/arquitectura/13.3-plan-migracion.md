## 1. Principios del plan [RECOMENDACIÓN]

1. **Sin «big bang».** Se usa el patrón **expandir → convivir → contraer** que el proyecto ya usó:
   - 0015 publicación sin moderación, con su guarda;
   - 0016 «contracción».

   [CONFIRMADO POR CÓDIGO]
2. **Inundación primero se vuelve módulo sin cambiar su comportamiento.** La suite actual y la E2E
   son la red de seguridad.
3. **Las categorías nuevas se encienden una por una** desde el catálogo. Mientras haya una sola
   activa, el selector no se muestra: **cero cambios visibles**.
4. **Toda tarea sigue CLAUDE.md §12.4**:
   - plan aprobado;
   - reparto por nivel: las tareas raíz son contratos, esquema, visibilidad y severidad;
   - verificación SDD.
5. **Cada fase deja `main` desplegable** y con las pruebas en verde.

## 3. Migración de los reportes existentes

### 3.1 Qué se conserva y cómo [CONFIRMADO POR CÓDIGO + RECOMENDACIÓN]

| Dato | Cómo se conserva |
|---|---|
| **ID** (`uuid`) | No se toca: `RENAME TABLE` y `ADD COLUMN` no reescriben las claves |
| **Fotos** | `reporte_foto.reporte_id` es una FK por OID y sobrevive al renombre. Los objetos `<uuid>.webp` no cambian de clave |
| **Auditoría** | Ya usa `entidad = 'reporte'` y `entidad_id = id`: el historial sigue enlazado. Se suma la acción `categoria:activar` |
| **Fechas** | `creado_en`, `publicar_en`, `evento_en`, `validado_en`, `actualizado_en`: intactas |
| **Ubicación** | `geom`, `geom_publico`, `distrito_id`, `unidad_vecinal_id`, `version_capa`, `resolucion_flags`, `ubicacion_*`: intactas |
| **Estados** | `estado`, `estado_motivo`, `fusionado_en_id`, `validado_por`: intactos |
| **Severidad** | `severidad_*`: intactas. `severidad_version = 2` pasa a leerse como «inundación v2» |
| **Idempotencia** | `idempotencia.reporte_id`: FK por OID, intacta |
| **Puntos críticos** | `punto_critico.categoria = 'inundacion'` para los existentes. El recálculo completo con `PARTITION BY categoria` debe dar **los mismos grupos** (prueba) |
| **Campos de inundación** | Se **copian** al `detalle`; las columnas quedan hasta M10 |

### 3.2 Pasos de la migración de expansión (M2)

Conceptual, en una transacción y con guarda:

```text
0. GUARDA: abortar si hay reportes con campos de inundación nulos que deberían existir
   (patrón de la 0015).
1. CREATE TABLE categoria; INSERT inundacion (activa = true) y bache, area_verde, basura
   (activa = false).
2. ALTER TABLE reporte_inundacion RENAME TO reporte.
3. ADD COLUMN categoria text NOT NULL DEFAULT 'inundacion' REFERENCES categoria;
   ADD subtipo, detalle jsonb DEFAULT '{}', detalle_version smallint DEFAULT 1;
   CHECK detalle es objeto.
4. UPDATE reporte SET detalle = jsonb_build_object('profundidad_estimada', …, 'frecuencia', …,
   'causa_presunta', …, 'sumidero_cercano', …, 'sumidero_estado', …, 'agua_brota_sumidero', …).
   Por lotes si el volumen lo pide.
5. Los campos de inundación pasan a NULL-ables con
   CHECK (categoria <> 'inundacion' OR (profundidad_estimada IS NOT NULL AND frecuencia IS NOT NULL)).
6. CREATE VIEW reporte_inundacion AS SELECT * FROM reporte WHERE categoria = 'inundacion'
   WITH CHECK OPTION; GRANT igual que la tabla.
7. ALTER TABLE punto_critico ADD categoria … DEFAULT 'inundacion'.
8. Índices nuevos (13.2 §5.3), según lo medido.
```

**Por qué la vista de compatibilidad** [RECOMENDACIÓN]:

- Una consulta olvidada que siga diciendo `reporte_inundacion` **solo verá inundaciones**: no
  contamina.
- Un `INSERT` viejo sigue funcionando (vista actualizable de una tabla, con `DEFAULT 'inundacion'`).
- Permite desplegar la migración antes que el código nuevo.

### 3.3 Verificación de la migración (en una copia, antes de producción)

| Comprobación | Esperado |
|---|---|
| `count(*)` por `estado` | Igual antes y después |
| Fotos, auditoría, idempotencia y puntos críticos | `count(*)` igual |
| `md5(string_agg(id::text \|\| estado \|\| ST_AsText(geom) \|\| …, ',' ORDER BY id))` sobre las columnas no tocadas | Mismo valor |
| Los campos de inundación reconstruidos desde `detalle` | Iguales a las columnas, en el 100 % de las filas |
| `SELECT … FROM reporte_inundacion` | Igual a `SELECT … FROM reporte WHERE categoria = 'inundacion'` |
| Suites de `api-core` y `geo-service` (sin cambiar código) | Verdes contra la base migrada, gracias a la vista |
| Respaldo | Cifrado y **restauración ensayada** antes de aplicar (perfil `respaldos`) |

### 3.4 Plan de vuelta atrás

| Etapa | Cómo se vuelve |
|---|---|
| **M2** | Reversible mientras **no existan** reportes de otra categoría: borrar la vista, las columnas y el catálogo; renombrar de vuelta. Migración inversa probada |
| **M3–M5** | Código desplegable hacia atrás: la vista sostiene al código viejo |
| **Desde M6** (hay reportes de otras categorías) | Volver atrás exige **archivar** esos reportes. Por eso M6 se activa primero en local y en piloto |
| **M10** | No se ejecuta hasta que la ventana de compatibilidad esté cerrada y medida |

## 4. Plan de pruebas

### 4.1 Unitarias (Vitest)

**Por cada definición de categoría:**

- esquema válido e inválido (incluido Zod **estricto**: claves desconocidas rechazadas);
- tabla de severidad, como la de §9.1;
- `camposPublicos ⊆ claves del esquema`.

**Del registro** (pruebas de invariantes):

- slugs únicos y en `snake_case`;
- **contraste** de `c7` contra blanco ≥ 4,5 y contra el mapa ≥ 3 (cálculo WCAG en la prueba, como el
  de 13.1);
- el icono existe en `lucide-react`;
- cada filtro apunta a un campo real.

### 4.2 Integración API (api-core con PGlite)

- `POST /reportes` válido por categoría.
- `POST` con la **forma vieja** → `inundacion`.
- Categoría inactiva → `422`.
- Fusión entre categorías → `409`.
- **La prueba de tabla de visibilidad** (que hoy recorre todas las rutas) suma la dimensión
  `categoria`: rutas × estados × categorías.

### 4.3 Base de datos

- `migracion-00NN` desde cero e idempotente.
- Prueba de relleno y de vista de compatibilidad (§3.3).
- Migración inversa.
- `pnpm --filter db privilegios` en verde.

### 4.4 PostGIS

- **DBSCAN particionado**: un bache y una inundación a 5 m **no** forman un grupo.
- El recálculo da los mismos grupos que antes para inundación.
- Agregados por UV y por categoría.
- El PIP no cambia (capa sintética de `geo-service`).

### 4.5 No contaminación

Prueba explícita: la semilla pone reportes de **las cuatro categorías en las mismas coordenadas**.

- `GET /reportes?categoria=bache` devuelve **solo** baches.
- Sin parámetro devuelve **solo** inundaciones.
- `/exportar`, `/indicadores`, `/ejecutivo`, agregados y puntos críticos, igual.
- La vista `reporte_inundacion` no ve baches.

### 4.6 E2E (Playwright, `e2e/`, runner local)

- Al entrar, Inundaciones activa.
- Cambiar a Baches:
  - URL `?categoria=bache`;
  - solo pines de bache, con la semilla superpuesta;
  - **centro y zoom iguales**;
  - selección limpia;
  - anuncio `aria-live`.
- Volver a Inundaciones: sin parpadeo de puntos ajenos.
- Reportar un bache de punta a punta.
- Flujo de inundación actual intacto.
- Panel: filtrar por categoría → validar → exportar.

### 4.7 Visual y accesibilidad

- Capturas por categoría en celular y escritorio.
- `axe` por categoría.
- Foco visible y objetivos de 48 px en el selector.
- Navegación del `tablist` con flechas.
- Lector de pantalla en el cambio de categoría.

### 4.8 Rendimiento

- `banco-datos` y `banco-carga` con **4 categorías** (hay que adaptarlos en su momento: es código,
  M9).
- `EXPLAIN` del listado y de los agregados con 1 M de filas.
- Medir que **el cambio de categoría** no supere el presupuesto de interacción (de caché: inmediato;
  de red: menos de 1 s en 4G) [PENDIENTE DE DECISIÓN].

### 4.9 Seguridad (`sdd-auditor`)

- Tamaño máximo del `detalle`.
- Sin texto libre nuevo fuera de `descripcion`.
- `camposPublicos`: nada privado en la vista pública.
- Cupos con 4 categorías.
- Aviso de emergencia.
- Fotos con personas (aviso).
- La categoría no se puede cambiar después de crear el reporte (o solo el técnico, con auditoría)
  [PENDIENTE DE DECISIÓN].

### 4.10 Migración

El ensayo de §3.3 sobre una copia de la base real, con el resultado anotado.

## 5. Criterios de aceptación

### Categorías

- [ ] Inundaciones es la categoría inicial al abrir `/` sin parámetros.
- [ ] Se puede cambiar a Baches, Áreas verdes y Basura desde el selector, con teclado y con lector
  de pantalla.
- [ ] La URL refleja la categoría y abrir esa URL la restaura.
- [ ] El mapa muestra **solo** reportes de la categoría activa, también en clusters y agregados por
  UV.
- [ ] Los filtros, la leyenda, los iconos y el botón «Reportar…» corresponden a la categoría.
- [ ] Al cambiar se conservan centro y zoom; se limpia la selección; se cierra el detalle.
- [ ] Una categoría inactiva en la instalación no aparece en el selector ni se acepta en la API.

### Reportes

- [ ] El flujo de creación es el mismo en todas: ubicación, «qué pasa», foto, revisión.
- [ ] Solo el paso «Qué pasa» cambia, y se genera desde la definición.
- [ ] Siguen aplicando en todas:
  - fotos solo con la cámara, WebP sin metadatos;
  - radio de 60 m y ubicación aproximada;
  - cupos e idempotencia;
  - publicación diferida;
  - «NO SE HA VERIFICADO»;
  - jitter.
- [ ] La severidad se calcula en el servidor con la función de la categoría y usa la escala común.
- [ ] La fusión solo es posible dentro de la misma categoría.

### Datos y migración

- [ ] Todos los reportes existentes conservan ID, fotos, auditoría, fechas, ubicación, estado y
  severidad (§3.3).
- [ ] Una consulta con el nombre viejo de la tabla solo ve inundaciones.
- [ ] Los clientes que no envían `categoria` siguen funcionando como hoy.

### Arquitectura

- [ ] No existen apps, APIs ni bases duplicadas por categoría.
- [ ] El núcleo no tiene ramas `if (categoria === …)` fuera del registro y de los componentes
  especiales registrados.
- [ ] Agregar una quinta categoría de prueba (solo en las pruebas) requiere ≤ 8 archivos nuevos y
  ≤ 3 líneas de registro, sin tocar el núcleo. Se verifica con una «categoría sintética» en la suite.

### Calidad

- [ ] lint, typecheck, test y build en verde.
- [ ] E2E G1–G5 y las nuevas pruebas de categoría en verde.
- [ ] `axe` sin violaciones nuevas.
- [ ] Contraste de la paleta verificado por prueba.
- [ ] OpenAPI regenerado y CHANGELOG de `contracts` al día.
